Redis is a shared dictionary that lives in its own program

Your win today: explain what Redis is to a friend in one sentence, name the jobs companies use it for, and build a working rate limiter with two commands on the real Redis already installed on your Mac.

Predict first

Guess. Being wrong now makes the right answer stick later.

1. Your Python program stores a shopping cart in a dict. The program restarts. What happens to the cart?

A dict lives in your process's memory. When the process ends, the operating system takes that memory back. Nothing was ever written down.

2. A website runs on two machines, A and B, each with its own dict of carts. You add a shoe on A, then your next click lands on B. What do you see?

Two processes never share memory by accident. B's dict is a completely different object. This is the exact problem Redis exists to solve.

The problem a dictionary cannot solve

You already know the most useful data structure in programming: a dictionary. Give it a key, get back a value. Python's dict does this in about the same time whether it holds ten items or ten million.

But a dict has two limits. It dies with your program, and only your program can see it. Real websites run the same code on many machines at once so they can serve many people. Each copy has its own private memory.

The fix is almost silly once you see it. Take the dictionary out of your program and put it in its own program, on its own machine if you like. Every app server asks that one program for data, over the network. Now there is exactly one cart, and every server sees it.

Redis = a dictionary that lives in its own program and answers questions over the network.

The name says it: REmote DIctionary Server. [Redis FAQ] It keeps everything in memory (RAM), which is why it is fast, and it can also write to disk so data survives a restart. [Redis persistence docs]

Six words you will use every day

Each word gets a picture. Come back here whenever one feels fuzzy.

Key and value A label and the thing it points to. The key is the name you look up by. The value is what comes back. Keys in Redis are usually written with colons, like user:42:name, purely as a naming habit.
Server A program that waits for questions and answers them. It runs forever and never shows a window. Redis is a server.
Client Whoever asks the server a question. Your web app is a client of Redis. So is redis-cli, the little terminal program you will use today.
In-memory Kept in RAM, not on disk. RAM is the computer's short-term memory: very fast, but wiped when power goes. Redis keeps data in RAM and copies it to disk on the side.
Port A numbered door on a computer. One machine runs many servers, each listening at its own door. Redis listens at door 6379 by default.
Command One instruction sent to Redis. The first word is the verb (SET, GET, INCR). The rest are its arguments. Redis answers each command with exactly one reply.

What companies actually use it for

Redis is less a database you store everything in and more a fast shared scratchpad that sits next to your real database. Here are six everyday jobs. Notice that each one is just a few commands.

Do it: play with the real Redis

Redis is already installed on your Mac (redis-server 8.4). A senior engineer building a clone starts here, because the real thing is the answer key. Every command you implement later, you will run against real Redis first and copy its exact reply.

Step 1. Open a terminal in Cursor (Ctrl+`) and start a Redis server on a spare port so it does not clash with anything: 
$ redis-server --port 6399 --save ''
It prints a logo and Ready to accept connections, then just sits there. That is a server waiting. Leave it running.
Step 2. Open a second terminal tab. This one is the client: 
$ redis-cli -p 6399
127.0.0.1:6399> PING
PONG
127.0.0.1:6399> SET user:42:name "Ada"
OK
127.0.0.1:6399> GET user:42:name
"Ada"
127.0.0.1:6399> GET nope
(nil)
(nil) means "no such key". That is the Redis version of Python's None.
Step 3. Your win: a rate limiter. Pretend Ada makes requests during the 12:00 minute. Each request bumps a counter: 
127.0.0.1:6399> INCR rate:ada:1200
(integer) 1
127.0.0.1:6399> INCR rate:ada:1200
(integer) 2
127.0.0.1:6399> EXPIRE rate:ada:1200 60
(integer) 1
127.0.0.1:6399> TTL rate:ada:1200
(integer) 57
INCR creates the key at 0 if it is missing and adds 1. EXPIRE sets a self-destruct timer. TTL ("time to live") shows the seconds left. Your app's rule is one line: if the number INCR returns is over 100, refuse. Wait a minute and run GET rate:ada:1200 again. It is gone.
Step 4. Try two of the other jobs: 
127.0.0.1:6399> ZADD leaderboard 120 ada 95 bob 140 cy
(integer) 3
127.0.0.1:6399> ZRANGE leaderboard 0 -1 REV WITHSCORES
1) "cy"
2) "140"
3) "ada"
4) "120"
5) "bob"
6) "95"
127.0.0.1:6399> LPUSH jobs "email:ada" "email:bob"
(integer) 2
127.0.0.1:6399> RPOP jobs
"email:ada"

Peek under the hood

Here is the secret that makes this whole course possible. redis-cli is not magic. It sends plain text over a network connection. You can talk to Redis with nc (netcat), a tool that just shovels raw bytes into a connection:

$ printf 'PING\r\n' | nc localhost 6399
+PONG

The \r\n is two invisible characters that mean "end of line" (carriage return, line feed). Redis replied with +PONG and its own \r\n. The + is a one-character tag that means "a simple string follows". That little set of rules is called RESP, the Redis Serialization Protocol. [RESP spec]

So to build Redis you need four things, stacked like floors of a building. You will build them in this order:

Do not start by designing classes. Start by watching the real system and writing down exactly what it does: which bytes go in, which bytes come out. That record becomes your test suite. Then build the thinnest possible slice that works end to end (one connection, one command, PING), and grow it one floor at a time. A clone you can test against the original from day one never drifts far from correct.

"Can Python be as fast as Rust here?"

You asked this, and the honest answer is: partly, and the part you can get is the part that matters most.

  • Most of Redis's speed is design, not language. Redis runs its commands on a single thread, one after another, and stays fast because everything is in memory and nothing makes it wait. [Redis latency docs] That design (one loop juggling many connections) is exactly what Python's asyncio gives you, and it is the same model the Tokio tutorial teaches in Rust. You will copy the design directly.
  • The language tax is real. Python does more work per instruction than Rust or C, so a Python clone will be slower per command. We will measure that gap with redis-benchmark instead of guessing.
  • Then we claw it back, in order of cheapness: batching many commands per network trip (pipelining), a faster event loop (uvloop), several Python processes sharing the load, and finally rewriting the one function the profiler blames in Rust and calling it from Python with PyO3. That last step is where the Rust sources come back in.

Check yourself

3. Why does keeping data in RAM make Redis fast?

RAM is far quicker to read and write than a disk. The catch is that it forgets everything when power goes, which is why Redis also copies data to disk.

4. Which pair of commands builds a rate limiter?

INCR counts requests, EXPIRE throws the counter away when the time window ends. ZADD/ZRANGE is a leaderboard, LPUSH/RPOP is a queue.

5. What does redis-cli really send to the server?

It sends bytes following the RESP rules, which you saw with nc. Anything that can send those bytes can talk to Redis, including the server you are about to write.

6. Why start the project by poking the real Redis?

Real Redis tells you the exact correct reply for any command. You will test sat-redis against it, so your clone behaves like the original.

7. In your own words, without scrolling up: what problem does Redis solve that a Python dict cannot? Use the shopping cart example.

Model answerA dict lives inside one program, so other programs (like a second web server) cannot see it, and it disappears when the program stops. Redis moves the dictionary into its own program that every server talks to over the network, so there is one shared cart, and it can save to disk so the cart survives restarts.
