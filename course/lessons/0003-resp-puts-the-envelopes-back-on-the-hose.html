RESP puts the envelopes back on the hose

Your win today: you catch the exact bytes redis-cli sends, then write the parser that turns them into a Python list like [b"ECHO", b"hi"], even when they arrive in pieces. 23 new tests go green. No sockets today: just bytes in, values out.

Predict first

1. Bytes arrive as one long stream with no gaps. What is the most reliable way for the receiver to know where a message ends?

Pauses depend on the network and lie. recv chunks are random, as lesson 2 showed. Fixed sizes waste space. Saying "the next 5 bytes are the message" always works, whatever is inside those bytes. RESP does exactly this for its data.

2. You split the incoming bytes at every \r\n to find messages. A user stores a value that itself contains \r\n. What goes wrong?

A separator only works if it can never appear inside the data. Users can store anything, including \r\n and raw image bytes, so RESP announces the length of each value instead of relying on a separator to end it.

Where we are

The problem: a hose with no envelopes

Remember lesson 2: TCP is a hose. It delivers bytes in order, but it forgets where one message ended and the next began. Your echo server got away with that because it never needed to understand anything. A real server must know "this is one whole command, run it now". So the two sides agree on a way to draw the envelope lines back in. That agreement is called a framing rule, and there are only three basic ones:

See it with your own eyes

Before reading any more spec, catch the real bytes. nc -l makes nc act as a fake server that prints whatever arrives, and od -c shows every byte, including the invisible ones.

Catch redis-cli in the act. In one terminal tab: 
$ nc -l 6390 | od -c
In a second tab: 
$ redis-cli -p 6390 ECHO hi
redis-cli will sit waiting for a reply that never comes. Press Ctrl+C in both tabs. The first tab shows: 
0000000    *   2  \r  \n   $   4  \r  \n   E   C   H   O  \r  \n   $   2
0000020   \r  \n   h   i  \r  \n
That is the whole of what you typed, as 22 bytes. By the end of this lesson every one of them will make sense, and your code will turn them into [b"ECHO", b"hi"].

Reading those 22 bytes

CRLF, \r\n The "end of line" mark. Two invisible bytes, carriage return then line feed, borrowed from typewriters. In RESP it "always separates its parts". [spec]
Frame One whole message, envelope and all. A frame can contain other frames, as an array contains its items. Your parser's job is to cut exactly one frame off the front of the bytes.
Simple string, + A short status word. Text up to the \r\n. It "mustn't contain a CR or LF", which is why it needs no length. [spec] In Python: str.
Error, - A simple string that means "that went wrong". Shaped exactly like +, but a client must treat it as a failure. So in Python it gets its own type, Error.
Integer, : A whole number written as digits. May be negative. Python's int() happily reads bytes: int(b"-7") is -7.
Bulk string, $ Any bytes at all, length first. The workhorse: keys, values and command names are all bulk strings. Python: bytes, never decoded, because a value might be an image.
Null "There is nothing here." Length -1. GET on a missing key replies with this. It is different from an empty string (length 0), and a client "should return a nil object" for it. [spec]
Array, * A count, then that many frames, back to back. The items can be any type, including more arrays. Python: list.

The three answers a parser can give

Here is the idea the whole lesson hangs on. When you hand the parser some bytes, there are exactly three possible situations, and mixing them up is the classic bug.

Notice why parse returns a pair (value, bytes_used) instead of just the value. A null bulk string's value is None. If "not enough bytes yet" were also None, you could not tell them apart. With the pair, a null comes back as (None, 5) and "wait" comes back as plain None. The byte count also tells the caller exactly how much to cut off the front of its buffer.

The type map

RESPOn the wirePython value
simple string+OK\r\n"OK" (str)
error-ERR oops\r\nError("ERR oops")
integer:42\r\n42
bulk string$5\r\nhello\r\nb"hello" (bytes)
null$-1\r\n or *-1\r\nNone
array*2\r\n + 2 frames[…] (list)

The Python types carry the RESP type, so encode can go back the other way: a str becomes +, a bytes becomes $. Lesson 4 leans on that: replying "PONG" sends +PONG\r\n, and replying b"Ada" sends $3\r\nAda\r\n.

The spec

The tests are already in your repo at tests/test_resp.py. Run them first and watch them fail: uv run pytest -v tests/test_resp.py. Then create sat_redis/resp.py with exactly these four names:

NameWhat it must do
ErrorA class for error replies. Make it a subclass of str, so Error("ERR x") == "ERR x" but isinstance(e, Error) still tells it apart.
ProtocolErrorAn Exception subclass, raised when the bytes are not valid RESP.
parse(buf)Given bytes, return (value, bytes_used) for the first frame, or None if the frame is not complete yet. Raise ProtocolError on garbage. Never change or eat the bytes after the frame.
encode(value)Turn a Python value back into RESP bytes, using the type map. Raise TypeError for anything else, such as a float.
TestsThe lesson inside them
simple_string … nested_arrayOne test per type. The nested one proves arrays can hold anything, arrays included.
bulk_string_may_contain_crlfThe length decides where data ends, not the next \r\n. This test fails any parser that splits on separators.
empty_bulk_string_is_not_nullb"" and None are different answers. GET on an empty value and GET on a missing key must look different.
every_partial_frame_means_wait_for_moreThe hose, tested properly: each frame is cut at every possible byte, the way recv might cut it, and each cut must return None. That covers 70 cases in about ten lines.
leaves_the_next_frame_alone, back_to_back_frames…The byte count lets the caller pull frames out of a buffer in a loop and keep the unfinished tail.

encode_each_type, round_tripWhatever encode writes, parse must read back to the same value. Round trips catch bugs in either half.

Build it in five steps

Run just the step you are on with -k. Try each step before opening a hint, and open hints one rung at a time.

Step A: Error, ProtocolError, encode. Writing is easier than reading, so start there. Goal: uv run pytest -v tests/test_resp.py -k encode is green except round_trip, which needs parse.
Hint 1: the shapeOne if isinstance(...) branch per row of the type map, each returning bytes. An array encodes its header, then encode of each item, joined. That is recursion, and it is fine: the items encode themselves.
Hint 2: the trapError is a subclass of str, so isinstance(Error("x"), str) is True. If the str check comes first, errors go out as +ERR…. Check the more specific type first. Also: bytes formatting works, b"$%d\r\n" % 5 gives b"$5\r\n".
Step B: the line types, + - : Goal: -k "simple or error_is or integers" green.
Hint 1: find the end of the linebuf.find(b"\r\n") gives the index of the first \r\n, or -1 if there is none yet. No \r\n means the line is incomplete, so return None.
Hint 2: the type byteCareful: buf[0] on bytes gives an int (43), not b"+". Use a slice, buf[0:1], to compare against b"+". The bytes used are "up to and including the \r\n", so the end index plus 2.
Step C: bulk strings and nulls. Goal: -k "bulk or null" green.
Hint 1: two readsFirst read the header line, as in step B, to get the length n. Then the data is the next n bytes, followed by \r\n. If the buffer is shorter than that, return None. Do not search for \r\n to find the end of the data. Count.
Hint 2: the edgesn == -1 means null: return (None, bytes_used). After the n data bytes, check that the next two bytes really are \r\n. If they are something else, the sender lied about the length: raise ProtocolError.
Step D: arrays, and the partial-frame test. Goal: -k "array or partial or frame" green.
Hint 1: where the trouble isAn array's items start partway into the buffer, not at index 0. Slicing out buf[pos:] for each item works, but it copies the rest of the buffer every time. Instead, give your real parser a starting position: a helper _parse_at(buf, pos) that returns (value, next_pos) or None. Then parse(buf) is just _parse_at(buf, 0), and bytes.find(sub, start) takes a start position too.
Hint 2: pseudocode for arrays 
read header line → count, pos
if count == -1: return (None, pos)
items = []
repeat count times:
    result = _parse_at(buf, pos)
    if result is None: return None     # an item is incomplete, so the array is
    value, pos = result
    append value to items
return (items, pos)
If any single item is incomplete, the whole frame is. That one return None is what makes all 70 partial cuts pass.
Step E: garbage. Goal: uv run pytest -v shows 30 passed, 1 xfailed (the 7 echo tests still pass).
Hint 1: two kinds of garbageA type byte that is not one of + - : $ * should raise ProtocolError. And int(b"abc") raises ValueError: catch that and raise ProtocolError instead, so callers only ever deal with one error type for bad input. Put the conversion in a small helper so you write that try once.

Four habits here. First, keep the protocol pure: parse and encode never touch a socket, so 23 tests run in milliseconds and none of them can fail because of the network. The socket code (lesson 2) and the protocol code (today) meet in exactly one place, next lesson. Second, test the hose by brute force: instead of guessing which splits are tricky, cut every frame at every byte. It costs a loop and finds the bugs you would never think to write a test for. Third, "not yet" and "never" are different answers: None means read more, ProtocolError means hang up. A parser that confuses them either hangs forever on garbage or drops honest clients on a slow network. Fourth, leave it crude on purpose: if a 100 MB value arrives in 1 KB chunks, this parser re-reads from the start on every chunk, which gets slow for huge frames. That is fine for now. Tokio's mini-redis has the same "check, then parse" shape. You will measure before you optimise, in lesson 13.

Check yourself

3. Why does a bulk string carry its length instead of just ending at \r\n?

Values can be any bytes at all, including \r\n and images. A length lets the reader count past them. That is what "binary-safe" means.

4. parse(b"$5\r\nhel") should give back what?

Nothing is wrong yet. Five bytes were promised and only three have arrived. The caller should recv more and try again with the bigger buffer.

5. What does redis-cli actually send when you type GET user:42?

*2\r\n$3\r\nGET\r\n$7\r\nuser:42\r\n. Every command is an array of bulk strings, one per word. You caught exactly this shape with nc.

6. Why does parse return (value, bytes_used) rather than just the value?

A null's value is None, and "not enough bytes" is also None. Wrapping real results in a pair keeps them apart, and the count tells the caller how much of its buffer to cut off. That makes two good reasons for one small design choice.

7. Without scrolling up: explain the three things parse can do with a buffer, and what the caller should do after each.

Model answerIf the buffer starts with a whole frame, parse returns (value, bytes_used): the caller handles the value, cuts that many bytes off the front, and tries again, because another frame may be waiting. If the buffer holds only part of a frame, it returns None: the caller keeps the bytes, calls recv for more, appends them, and tries again. If the bytes are not valid RESP, it raises ProtocolError: waiting will never fix that, so the caller should send an error and close the connection.
