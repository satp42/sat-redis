A server is a loop that answers the phone

Your win today: the first real piece of sat-redis. You write an echo server with nothing but Python's standard library, turn 7 tests green, and watch the real redis-cli connect to it.

Predict first

1. A client sends 1,000,000 bytes in one go. Your server calls recv(1024) once. What does that one call give you?

The number you pass to recv is a maximum, not a promise. You get whatever has arrived, up to that many bytes, and you call it again for the rest.

2. Your server is busy talking to client A. Client B connects. With the simple loop you build today, what happens to B?

The operating system lets B connect and parks it in a queue, but your code only picks up the next call when it finishes the current one. B sits on hold. You will prove this today and fix it in lesson 5.

Where we are

The phone call picture

Two programs talking over a network work almost exactly like a phone call to a big office. Hold this picture and every socket call has an obvious meaning.

IP address, localhost The street address of a computer. 127.0.0.1, also called localhost, always means "the machine I am on", so your client and server can both run on your laptop.
Port The door number on that address. Real Redis uses 6379. sat-redis will use 6380 so both can run side by side for comparison.
Socket The phone handset your program holds. A Python object you read bytes from and write bytes to. Each end of a conversation has its own.
bind, then listen Claim a door, then start answering it. bind((host, port)) attaches the socket to an address. listen() turns it into a receptionist with a small waiting queue.
accept Pick up the next ringing call. It waits (blocks) until someone connects, then returns a brand-new socket just for that caller, plus the caller's address.
recv and sendall Listen and speak. recv(n) returns up to n bytes that have arrived. sendall(data) keeps sending until every byte has gone, unlike plain send, which may stop early. [socket docs]
Hang-up: recv returns b"" Silence that means goodbye. "When a recv returns 0 bytes, it means the other side has closed … You will not receive any more data on this connection. Ever." [HOWTO]
Reset: the slammed phone The caller vanished mid-sentence. A crashed client does not say goodbye. Your next recv or sendall raises ConnectionResetError. A server must shrug that off and take the next call.

The whole conversation, in order

The one idea that bites everyone: TCP is a hose, not envelopes

When the client sends "PING" and then "SET k v", you might picture two envelopes arriving. That is not what happens. TCP, the protocol underneath every socket here, delivers one continuous stream of bytes, like water through a hose. The boundaries between the client's sends are not kept.

For an echo server this does not matter yet, because you send back whatever chunk you got and the bytes stay in order. In lesson 3 it becomes the problem: to understand a Redis command you have to find where one command ends and the next begins. Notice it now so it is not a surprise then.

The spec

Create sat_redis/server.py with exactly these pieces:

PieceWhat it must do
make_server(host, port)Create a TCP socket, turn on SO_REUSEADDR, bind it, start listening, and return it. Do not accept anything here.
serve_forever(server)Loop forever: accept a client, echo everything it sends until it hangs up, close it, accept the next one. A client that vanishes rudely must not stop the loop.
if __name__ == "__main__":Run serve_forever(make_server("127.0.0.1", 6380)), so uv run python -m sat_redis.server starts it.

And here is what each test is really checking:

TestThe lesson inside it
make_server_returns_a_listening_socketSetup is separate from serving. That split is what makes the server testable.
echoes_one_messageThe basic loop works.
echoes_many_messages_on_one_connectionThe inner loop keeps going until hang-up, not after one message.
bytes_come_back_untouchedBytes are bytes. No .decode(), no stripping \r\n, no text tricks.
echoes_a_payload_bigger_than_one_recvThe hose: 1 MiB arrives in many chunks, and every one must come back.
serves_the_next_client_after_one_hangs_upThe outer loop: after b"", close and accept again.
survives_a_client_that_vanishes_abruptlyOne crashing client must not take the server down for everyone else.
two_clients_at_the_same_time xfailMarked "expected to fail". It documents today's known limit. When lesson 5 fixes it, pytest will tell you to remove the mark.

Build it in three steps

Run only the tests for the step you are on with -k. Try each step before opening a hint. Open hints one rung at a time.

Step A: make_server. Goal: uv run pytest -v -k make_server goes green.
Hint 1: which callssocket.socket(socket.AF_INET, socket.SOCK_STREAM) makes a TCP socket (AF_INET = IPv4 addresses, SOCK_STREAM = TCP). Then setsockopt, bind, listen, in that order.
Hint 2: what SO_REUSEADDR is forAfter your server stops, the operating system keeps its old address reserved for a short while (a state called TIME_WAIT), so restarting immediately fails with "Address already in use". The flag "tells the kernel to reuse a local socket in TIME_WAIT state, without waiting for its natural timeout to expire". [socket docs] It must be set before bind: s.setsockopt(socket.SOL_SOCKET, socket.SO_REUSEADDR, 1).
Step B: serve_forever. Goal: the five echo tests go green: uv run pytest -v -k "echo or next_client".
Hint 1: the shapeTwo loops. The outer one calls accept(). The inner one calls recv and sendall until recv returns empty bytes. Consider putting the inner loop in its own function, say handle(conn).
Hint 2: pseudocode 
forever:
    conn, address = accept a call
    with conn:                      # closes it for you when the block ends
        repeat:
            data = up to 1024 bytes from conn
            if data is empty: stop  # they hung up
            send all of data back on conn
Python's walrus operator while data := conn.recv(1024): collapses the inner loop to two lines, if you like it.
Step C: survive rude clients. Goal: uv run pytest -v shows 7 passed, 1 xfailed.
Hint 1: what is going wrongRun the test and read the warning pytest prints. The server thread died with ConnectionResetError while handling the rude client, so nobody was left to answer the next one.
Hint 2: where to catch itCatch the error around the handling of one client, inside the outer loop, so only that conversation ends. ConnectionResetError and BrokenPipeError are both subclasses of ConnectionError, so catching that one name covers both kinds of slammed phone. Do not catch every exception: a real bug in your code should still crash loudly.

Try it live

Talk to it with nc. In one terminal tab: 
$ uv run python -m sat_redis.server
In a second tab, type lines and watch them come back: 
$ nc localhost 6380
hello
hello
See the limit with your own eyes. Leave that nc open and start a third tab with another nc localhost 6380. Type into it. Nothing comes back. Now quit the first nc with Ctrl+C. The third tab's text suddenly echoes. That is the "on hold" behaviour from prediction 2, and it is exactly what the xfail test records.
Your win: real redis-cli is already talking to you. With the server running: 
$ redis-cli -p 6380
127.0.0.1:6380> PING
1) "PING"
127.0.0.1:6380> SET user:42 Ada
1) "SET"
2) "user:42"
3) "Ada"
Why does that work? redis-cli sends your command as RESP bytes (an array of strings). Your server sends the same bytes straight back, which happens to be a perfectly valid RESP reply: an array containing your own words. So redis-cli prints them. It is a parrot, but it speaks Redis's language. Lesson 3 teaches you to read those bytes, and lesson 4 to answer properly.
Commit, like a professional. A green test suite is a checkpoint: 
$ git add pyproject.toml uv.lock sat_redis
$ git commit -m "Echo server: stdlib sockets, 7 tests green"
$ git push
Three habits are hiding in this lesson. First, split setup from the loop (make_server vs serve_forever), so tests can start a server on port 0, which means "OS, pick any free port". Tests then never clash with each other or with a server you left running. Second, test the failure paths, not just the happy one: the rude client and the huge payload are what break real servers, and they cost three lines each to test. Third, write the known limitation down as a test (the xfail) instead of a mental note. Future you gets told the day it is fixed.

Check yourself

3. What does a listening socket do all day?

The receptionist only answers and hands each caller a private line (accept returns a new socket). All reading and writing happens on those private lines.

4. Your inner loop's recv returns b"". What does that mean?

Empty bytes is TCP's goodbye. Nothing more will ever arrive on that connection, so close it and go back to accept.

5. Why use sendall instead of send?

Like recv, plain send may handle only part of what you give it and tell you how much. sendall loops for you "until either all data has been sent or an error occurs". [socket docs]

6. A client sends PING\r\n then SET k v\r\n. Which recv results are possible?

TCP is a hose: it keeps the order and never loses bytes, but it does not remember where one send ended. Lesson 3 is about putting the envelopes back.

7. Without scrolling up: explain the two loops in your server, and what event ends each one.

Model answerThe outer loop waits in accept() for the next client and never ends while the server runs. The inner loop reads with recv and writes everything back with sendall. It ends when recv returns b"" (the client hung up) or when the connection is reset (the client vanished). Then the server closes that connection and the outer loop accepts the next one.
